## 二、高危问题（会导致运行时错误 / 数据错误 / 安全漏洞）

### BUG-001：`listPosts` 参数顺序错乱（status 与 username 互换） — ✅ 已修复

- **描述**：`UserBehaviorAdminController.listPosts` 调用 Service 时实参顺序与 Service 方法签名不一致，导致状态筛选与用户名筛选互相错位。
- **定位**：
  - `relic-server/src/main/java/com/relic/controller/admin/UserBehaviorAdminController.java:74`
    ```java
    return Result.success(userBehaviorAdminService.listPosts(title, userId, status, username, startTime, endTime, page, pageSize));
    ```
  - Service 签名（`UserBehaviorAdminService.java:16`）：`listPosts(String keyword, Integer userId, String username, String status, ...)`
- **影响分析**：前端传 `status` 时实际被当作 `username` 过滤，传 `username` 时被当作 `status` 过滤。用户按"用户名"或"状态"筛选动态列表时结果完全错误，功能不可用。
- **修复方案**：调整实参顺序：
  ```java
  userBehaviorAdminService.listPosts(title, userId, username, status, startTime, endTime, page, pageSize)
  ```

### BUG-002：`listUploads` 参数顺序错乱（mediaType/status/username 整体错位） — ✅ 已修复

- **描述**：`UserBehaviorAdminController.listUploads` 调用 Service 时 `mediaType`、`status`、`username` 三个参数整体错位。
- **定位**：
  - `relic-server/src/main/java/com/relic/controller/admin/UserBehaviorAdminController.java:113`
    ```java
    return Result.success(userBehaviorAdminService.listUploads(userId, mediaType, status, username, startTime, endTime, page, pageSize));
    ```
  - Service 签名（`UserBehaviorAdminService.java:23`）：`listUploads(Integer userId, String username, String mediaType, String status, ...)`
- **影响分析**：上传记录列表的媒体类型、状态、用户名三个筛选条件全部错位，任何组合筛选都返回错误数据。
- **修复方案**：调整实参顺序：
  ```java
  userBehaviorAdminService.listUploads(userId, username, mediaType, status, startTime, endTime, page, pageSize)
  ```

### BUG-003：`ArtifactMapper.xml` 排序参数 `${}` 拼接导致 SQL 注入 — ✅ 已修复

- **描述**：文物分页查询的排序字段 `sortBy`/`sortOrder` 使用 `${}` 直接拼接，用户可注入任意 SQL。
- **定位**：`relic-server/src/main/resources/mapper/ArtifactMapper.xml:58-65`
  ```xml
  <choose>
      <when test="sortBy != null and sortOrder != null">
          ORDER BY ${sortBy} ${sortOrder}
      </when>
  ```
  入口：`AdminArtifactController.java:33-34`、`user/ArtifactController.java:29-30` 均直接透传前端参数。
- **影响分析**：攻击者可构造 `sortBy=1;DROP TABLE artifacts;--` 等恶意输入，造成数据泄露或破坏。`${}` 在 MyBatis 中是字符串拼接，不做转义。
- **修复方案**：排序参数改为白名单校验。在 Service 或 Controller 层过滤：
  ```java
  private static final Set<String> ALLOWED_SORT = Set.of("created_at","id","title_zh","title_en");
  private static final Set<String> ALLOWED_ORDER = Set.of("asc","desc");
  if (sortBy != null && !ALLOWED_SORT.contains(sortBy)) sortBy = "created_at";
  if (sortOrder != null && !ALLOWED_ORDER.contains(sortOrder.toLowerCase())) sortOrder = "desc";
  ```
  或将 `ORDER BY` 改为在 Java 侧根据枚举拼安全 SQL（不用 `${}` 传用户值）。

### BUG-004：管理员权限校验中 `selectByAdminUserId` 返回值未判空导致 NPE — ✅ 已修复

- **描述**：`AdminUserServiceImpl` 与 `UserServiceImpl` 中多处对 `adminUserRoleMapper.selectByAdminUserId(...)` 的返回值直接调用 `.getRoleId()`，未判空。若当前管理员未分配角色（数据库中无记录），即抛 NullPointerException。
- **定位**：
  - `relic-server/src/main/java/com/relic/service/impl/AdminUserServiceImpl.java`：第 65、100、121、137、151、163、186、210 行
    ```java
    AdminUserRole adminUserRole = adminUserRoleMapper.selectByAdminUserId(BaseContext.getCurrentId());
    if(!adminUserRole.getRoleId().equals(RoleConstant.SUPER_ADMIN)){ ... }
    ```

## 三、中危问题（数据不一致 / 逻辑错误 / 资源问题）

### BUG-008：`OperationLogAspect` 记录操作日志时 `userId` 可能取到 0 — ✅ 已修复

- **描述**：`getCurrentUserId()` 在 `BaseContext.getCurrentId()` 为空或非 Long/Integer 时返回 `0L`，且日志仍会记录一条 `userId=0` 的操作日志。
- **定位**：`relic-server/src/main/java/com/relic/aspect/OperationLogAspect.java:87-94`
- **影响分析**：匿名/未登录触发的带 `@OperationLog` 接口会产生误导性日志；`operationLogMapper.insert` 依赖 `userId` 外键时可能失败。
- **修复方案**：`userId` 为 0 时跳过记录或标记为系统操作；同时确认 `operation_logs.user_id` 是否允许为 0/空。

### BUG-009：`AuditSyncTask` 自动审核"转人工"状态语义混淆 — ✅ 已修复

- **描述**：`executeAutoReview` 在风险评分 ≥ 阈值时返回 `"rejected"`，随后 `syncPosts/syncComments/syncUploads` 中 `manualResult = "pending"`、`autoResult = "rejected"`。即"自动拒绝并转人工"被记为 `rejected`，与真正的人工拒绝含义冲突。
- **定位**：`relic-server/src/main/java/com/relic/task/AuditSyncTask.java:172-183`
  ```java
  } else {
      log.info("自动审核风险评分 {} >= 阈值 {}，转人工复核", ...);
      return "rejected";
  }
  ```
- **影响分析**：审核统计中无法区分"自动转人工"与"自动拒绝"，`approved/rejected/pending` 统计口径混乱，可能影响后续人工审核流程的初始化状态。
- **修复方案**：转人工时返回 `"pending"` 或新增 `"manual_review"` 状态，使 `autoResult` 与 `manualResult` 语义一致。

### BUG-010：`executeSqlFile` 恢复时逐条忽略错误导致半成功 — ✅ 已修复

- **描述**：`RestoreServiceImpl.executeSqlFile` 逐条执行 SQL，单条失败仅 `log.warn` 不中断，全部执行完后 `commit`。若中途有失败语句，最终提交的是"不完整恢复"。
- **定位**：`relic-server/src/main/java/com/relic/service/impl/RestoreServiceImpl.java:165-170`
- **影响分析**：备份文件含 `DROP TABLE` 后创建失败等场景下，数据库被删表后未完整重建即提交，造成不可恢复的数据损坏。
- **修复方案**：失败语句累计达到阈值（或遇到 `DROP TABLE`/`CREATE TABLE` 类语句失败）时抛异常回滚，并将错误写入恢复记录。

### BUG-011：`WebSocketServer` 使用非线程安全 `HashMap` 管理会话 — ✅ 已修复

- **描述**：`WebSocketServer` 用 `private static Map<String, Session> sessionMap = new HashMap();` 存会话，多连接并发 `put/remove` 时非线程安全；且使用 `System.out.println` 输出日志。
- **定位**：`relic-server/src/main/java/com/relic/websocket/WebSocketServer.java:22`
- **影响分析**：并发连接/断连时可能产生数据竞争、丢会话、死循环（HashMap 扩容时并发遍历）；线上排查日志不友好。
- **修复方案**：改用 `ConcurrentHashMap`，并使用 `@Slf4j` 日志：
  ```java
  private static final Map<String, Session> sessionMap = new ConcurrentHashMap<>();
  ```

### BUG-012：`RestoreServiceImpl.exportCurrentToFile` 对非字符串列错误加引号 — ✅ 已修复

- **描述**：应急备份导出时对**所有**列值都套用单引号 `'...'`（含数字、布尔列），而 `BackupServiceImpl.exportViaJdbc` 会按列类型区分。恢复时数值列被写入 `'123'` 字符串可能导致隐式转换或恢复失败。
- **定位**：`relic-server/src/main/java/com/relic/service/impl/RestoreServiceImpl.java:232-245`
- **影响分析**：恢复前应急备份 SQL 中数值字段带引号，虽 MySQL 多数情况可隐式转换，但 `0/1` 布尔、JSON、BLOB 等类型可能出错。
- **修复方案**：参考 `BackupServiceImpl` 的 `isStringType` 逻辑，仅字符串/日期列加引号。

### BUG-013：前端 `QaReviewTasksView` 审核人 ID 恒为 1 — ✅ 已修复

- **描述**：`localStorage.getItem('admin_id')` 恒为 `null`（登录时从未写入 `admin_id`），回退为 `1`，导致所有问答审核任务 `reviewerId` 恒为 1。

## 七、附录：扫描方法说明

1. **静态扫描**：对 `relic-server`、`relic-pojo`、`relic-common` 全部 Java 源文件、`resources/mapper/*.xml`、`application*.yml` 进行语法规范性与逻辑审查。
2. **前端扫描**：对 `relic-frontend/src` 全部 `.vue`、`.js` 文件进行引用一致性、生命周期、资源清理审查。
3. **交叉核验**：Controller → Service → Mapper → XML 全链路参数顺序、字段名、返回结构核对；前后端字段/请求头/token 键名核对。
4. **配置审查**：`application.yml`/`application-dev.yml` 前缀绑定、密钥长度、环境变量泄漏检查。
5. **SQL 脚本**：核对表结构（`admin_user_role`、`user_uploads`、`crawl_tasks`、`user_behaviors` 等）与实体/Mapper 字段映射一致性。

> 注：本文档仅记录静态扫描发现的问题，未执行运行时验证；修复后建议结合 `docx/测试报告.md` 中的用例回归测试。
