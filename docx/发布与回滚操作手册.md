## 二、发布流程（标准发布）

### 2.1 制品版本化
- **后端**：发布包 = `relic-server/target/relic-server-<version>.jar`，版本号与 git tag 一致；
- **前端**：发布产物 = `relic-frontend/dist/`，由 CI 构建并上传为 **GitHub Actions Artifact**，记录 `sha256`；
- 禁止使用本地手工构建产物作为发布制品。

### 2.2 数据库结构变更
- 所有结构变更通过 Flyway 脚本：`relic-server/src/main/resources/db/migration/V{n}__描述.sql`；
- **只允许追加新版本脚本，禁止修改已发布的历史脚本**；
- 发布时 Flyway 随应用启动自动迁移（`baseline-on-migrate=true` 对已有库生效）。

### 2.3 部署步骤
1. 拉取发布版本 jar / 前端 dist；
2. 核对环境变量（见 7 检查项），确认 `SPRING_PROFILES_ACTIVE=prod`；
3. 停旧进程 → 替换 jar/dist → 启动新进程；
4. 观察启动日志：Flyway 迁移成功、连接池就绪、无 ERROR；
5. 健康检查：`GET /v1/actuator/health` 返回 `UP`；
6. 冒烟：登录、核心页面、备份下载各验证一次。

## 三、回滚流程（Rollback）

### 3.1 触发条件
- 启动失败（依赖注入错误、Flyway 校验失败等）；
- 上线后核心功能不可用（登录失败、接口 500 频发）；
- 数据异常（迁移导致数据丢失或错乱）。

### 3.2 数据层回滚
> **原则：先恢复数据，再回退版本。**

| 场景 | 动作 |
|------|------|
| 结构变更导致数据异常 | 使用发布前备份（应急备份）执行 `恢复` 功能（仅超管） |
| Flyway 迁移失败 | 修复脚本后重新启动（Flyway 支持修复后继续），**不要手工删 flyway_schema_history** |
| 数据误删 | 用 `docx/发布前问题清单与处置记录.md` C-01 备份库恢复 |
| 需要撤销某次迁移 | 新增反向脚本 `V{n+1}__rollback_xxx.sql`，**禁止删除历史脚本** |

### 3.3 应用层回滚
1. 停止当前实例；
2. 用**上一版本 jar/dist**（保留至少最近 2 个版本）替换；
3. 若数据库结构已变更，确保旧版本应用可兼容（必要时使用反向脚本）；
4. 启动并验证登录与核心接口；
5. 记录回滚原因到变更日志。

### 3.4 快速回滚包
- 服务器保留目录：`/opt/relic/releases/`，存最近 2 个版本；
- 符号链接：`/opt/relic/current` → 当前版本，回滚时切换链接即可。
