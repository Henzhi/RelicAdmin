## 二、致命问题（Critical）— 发布前必须全部解决

### C-01 生产密钥明文硬编码于配置，存在直接泄露风险
- **优先级**：高
- **类别**：安全
- **现状**：`application-dev.yml` 硬编码数据库密码、阿里云 OSS AK/SK、4 个 JWT 密钥默认值（见 `docx/问题解决记录.md` ENG-001 后的残留）。
- **影响后果**：云数据库/OSS 被接管、任意伪造 Token、凭据随代码流转外泄。
- **解决步骤**：
  1. 轮换数据库连接账号密码、OSS AccessKey、全部 JWT 密钥（生成新值并立即作废旧值）；
  2. 删除 `application-dev.yml` 中 JWT 密钥的默认兜底值，改为必须注入环境变量；
  3. 将 dev 配置中的 DB/OSS 凭据移入本地环境变量或本地私有配置（不入库）；
  4. 用 `git log` 全量排查历史提交，确认该文件从未入库；若入库过需重写历史并同时轮换密钥。
- **状态**：已完成（配置侧 + git 历史清除）/ 需人工验证（云平台轮换）
- **解决结果**：
  1. JWT 4 个密钥已轮换为新随机值并写入 `application-dev.yml`；
  2. 数据库密码、OSS AK/SK 已从配置移除硬编码，改为环境变量注入（`MYSQL_PASSWORD`、`OSS_ACCESS_KEY_ID`、`OSS_ACCESS_KEY_SECRET`）；
  3. **git 历史复核（2026-08-04）**：泄露提交 `e5fa33c` 仅存于本地（远端 `team/main`、`origin/main` 均不包含，历史已由 `cc8d3f1` 提交重写）；已删除 filter-branch 备份 ref `refs/original/refs/heads/mahh`，`reflog expire --expire=now --all` + `git gc --prune=now`，验证 `git cat-file -t e5fa33c` 报 "not a valid object name"（对象已彻底移除）；
  4. **人工待办**：在 MySQL/阿里云控制台轮换真实密码与 AccessKey，确认 4 个 JWT 生产密钥与本地不同。
- **验证**：`git ls-files` 确认该文件当前未被跟踪；H-06 中应用已通过环境变量注入完整启动验证。

### C-02 OSS 工具初始化日志打印完整 AccessKey
- **优先级**：高
- **类别**：安全 / 日志
- **现状**：`OssConfiguration.java` 中 `log.info("开始创建阿里云文件上传工具类对象：{}", aliOssProperties)`，`@Data` 对象的 `toString()` 会输出 `accessKeyId` 与 `accessKeySecret`。
- **影响后果**：生产日志系统（云日志/ELK）中泄露云厂商密钥，扩大泄露面。
- **解决步骤**：
  1. 修改为仅打印脱敏信息（如 `endpoint/bucketName`，AK 只留前 4 位）；
  2. 复查启动日志确认无密钥输出；
  3. 若密钥已随日志进入日志平台，需一并轮换（与 C-01 联动）。
- **状态**：已完成
- **解决结果**：
  1. `OssConfiguration` 启动日志改为仅输出 endpoint/bucketName/AK 前 4 位脱敏值；
  2. `AliOssUtil` 中 `System.out.println` 错误输出改为 `log.error` 并脱敏（不打印 AK/SK 明细）；
  3. 验证：搜索确认无 `log.info(...aliOssProperties)` 全量打印。

### C-03 WebSocket 连接无任何鉴权
- **优先级**：高
- **类别**：安全
- **现状**：`WebSocketServer` 端点 `/ws/{sid}` 建立连接时不校验 JWT、不校验 `sid` 归属，仅将 session 放入内存 Map。
- **影响后果**：未授权连接建立；若未来按 `sid` 定向推送敏感数据即形成越权通道。
- **解决步骤**：
  1. 在 `onOpen` 中校验握手 URL 携带的 token（query 参数或 `Sec-WebSocket-Protocol`）；
  2. 校验失败即 `session.close(CloseReason)`；
  3. 将 `sid` 与 token 中用户身份绑定，禁止任意 sid 注入。
- **状态**：已完成（代码侧） / 需联调验证
- **解决结果**：
  1. `WebSocketServer` 增加 JWT 鉴权：从握手 query 取 `token`，用管理端密钥校验；
  2. `sid` 必须与 Token 内 `empId`/`id` 声明一致，不一致直接拒绝；
  3. 增加 `SpringConfigurator` 使端点实例可获取 Spring 容器 Bean；
  4. **人工待办**：前端接入时需在连接 URL 追加 `?token=<jwt>`（当前前端尚未使用该端点）；与前端联调时验证拒绝路径。

## 三、严重问题（High）— 发布前应全部解决

### H-01 登录接口无验证码 / 限流 / 失败锁定
- **优先级**：高
- **类别**：安全
- **现状**：全项目无 captcha、rate-limit、登录失败锁定；`SecurityLogService` 仅记录不拦截。
- **影响后果**：管理员与用户账号可被字典/撞库爆破。
- **解决步骤**：
  1. 引入图形/行为验证码（如 Hutool captcha 或独立验证码服务）；
  2. 对 4 个登录接口增加基于 IP + 账号的失败计数与滑动窗口限流；
  3. 连续失败 N 次锁定账号 T 分钟，并在 `SecurityLogService` 中记录；
  4. 通过 `AlertCheckScheduler` 或日志告警同步异常登录。
- **状态**：已完成（核心防护）
- **解决结果**：
  1. 新增 `LoginAttemptService`：账号+IP 连续失败 5 次锁定 15 分钟；IP 维度每分钟 >20 次尝试限流；
  2. 四个登录接口（admin/knowledge/museum/user）全部接入防护，登录成功清零计数；
  3. 通过 X-Forwarded-For / X-Real-IP 获取真实 IP；
  4. **待办**：图形/行为验证码需前端配合，后续迭代补充；`SecurityLogService` 对接后续完成。

### H-02 全局异常处理直接回显内部错误信息
- **优先级**：高
- **类别**：安全 / 代码质量
- **现状**：`GlobalExceptionHandler` 对 `RuntimeException` 直接返回 `ex.getMessage()`，可能包含 SQL、路径、内网地址。
- **影响后果**：攻击者可探测表结构、目录布局、内网拓扑。
- **解决步骤**：
  1. 新建 `BusinessException`/`BaseException` 统一承载对外提示文案；
  2. `RuntimeException` 分支改为返回通用文案（如"系统繁忙"），内部信息仅 `log.error`；
  3. 对 `IllegalArgumentException` 等确定安全的分支保留原样；
  4. 全项目业务抛错改为抛 `BaseException` 子类（与文档 BUG-026 的优化建议合并执行）。
- **状态**：已完成
- **解决结果**：
  1. `GlobalExceptionHandler` 的 `RuntimeException` 分支改为返回 `MessageConstant.UNKNOWN_ERROR`（"未知错误"），内部信息仅记录日志；
  2. `MultipartException` 分支同样不再回显内部消息；
  3. `BaseException`（含业务子类）与 `IllegalArgumentException` 仍返回明确文案，不影响正常业务提示。

### H-03 备份下载接口在文件不存在时自动创建"模拟文件"
- **优先级**：高
- **类别**：安全 / 数据完整性
- **现状**：`BackupAdminController.download` 在 `file.exists()` 为 false 时写占位文件并返回 200。
- **影响后果**：用户误以为备份成功，灾难恢复时发现备份不可用；该逻辑构成服务器任意路径写文件风险面。
- **解决步骤**：
  1. 删除"自动创建模拟文件"分支，文件不存在时返回 404 及明确错误信息；
  2. 对 `filePath` 做路径穿越校验（仅允许备份目录内）；
  3. 在下载前校验 `BackupRecord.status=1`（已完成）；
  4. 补充前端错误提示文案。
- **状态**：已完成
- **解决结果**：
  1. `BackupAdminController.download` 删除"自动创建模拟文件"逻辑；
  2. 增加三层校验：记录存在 → `status=1`（完成态）→ 文件真实存在；
  3. 新增路径穿越防护：仅允许文件位于备份存储根目录（`BackupService.getBackupRoot()`）之内；
  4. 越界/缺失/未完成均返回 404/403/409，不再写入任何文件。

### H-04 备份/恢复接口缺少超管权限校验（越权）
- **优先级**：高
- **类别**：安全 / 权限
- **现状**：`BackupServiceImpl`/`RestoreServiceImpl` 仅校验登录态，无 `requireSuperAdmin`；恢复会 `DROP TABLE` 重建全库。
- **影响后果**：任意已登录管理员可触发全库备份/恢复，属越权 + 数据破坏高危组合。
- **解决步骤**：
  1. 在 `createBackup/deleteBackup/restore` 等入口统一加 `requireSuperAdmin()`（复用 `AdminUserServiceImpl.isSuperAdmin` 模式或抽取公共鉴权工具）；
  2. 对 `RestoreConfirmDTO` 增加管理员密码二次确认（已实现，需核验覆盖所有入口）；
  3. 补充越权场景测试用例。
- **状态**：已完成（代码侧）
- **解决结果**：
  1. 新增公共组件 `SuperAdminGuard.requireSuperAdmin(message)`，复用 `AdminUserRoleMapper` 判断（未分配角色视为非超管，避免 NPE）；
  2. `BackupServiceImpl.createBackup`、`deleteBackup` 与 `RestoreServiceImpl.restore` 均加超管校验；
  3. 恢复接口原有的管理员密码二次确认保留；
  4. **待办**：补充越权测试用例（M-07 中安排）。

### H-05 CI 使用 Java 17 编译，项目要求 Java 21（环境不一致）

  3. 验证 `mvn -B compile && mvn -B test` 在 CI 全绿。
- **状态**：已完成（本地全量复现）
- **解决结果**：
  1. `ci.yml` 已由 Java 17 改为 Java 21（temurin）；
  2. 本地按 CI 步骤全量复现（2026-08-04）：`mvn compile` / `mvn test`（32 用例全绿）/ `mvn package` / Flyway 冒烟迁移（MySQL 8.0 全新库）全部通过；

### H-06 无版本化数据库迁移工具（Flyway/Liquibase）
- **优先级**：高
- **类别**：数据库迁移
- **现状**：仅靠 `seitem_结构.sql`（Navicat 导出）与手工 DDL，备份逻辑中残留 `flyway_schema_history` 排除。
- **影响后果**：结构变更无版本清单、无法自动升级/回退，多环境结构漂移。
- **解决步骤**：
  1. 引入 Flyway（`org.flywaydb:flyway-core` + `flyway-mysql`），版本适配 Spring Boot 3.2；
  2. 将现有 `seitem_结构.sql` 收敛为 `V1__init_schema.sql`，并对照实体与 Mapper 校验字段完整性；
  3. 建立后续变更规范：每次结构变更新增 `Vn__xxx.sql`，禁止改历史脚本；
  4. 配置 `spring.flyway.baseline-on-migrate=true`（对已有库做 baseline）；
  5. 清理备份任务中手动排除 `flyway_schema_history` 的逻辑（保留即可，但需确认与 Flyway 并存无冲突）。
- **状态**：已完成（联调验证通过）
- **解决结果**：
  1. `relic-server/pom.xml` 新增 `flyway-core` + `flyway-mysql`（版本由 Spring Boot 3.2.12 管理）；
  2. `application.yml` 配置 Flyway：`locations=classpath:db/migration`、`baseline-on-migrate=true`、`baseline-version=1`；
  3. 由 `seitem_结构.sql` 生成基线脚本 `db/migration/V1__init_schema.sql`（53 张表，已去除 DROP/SET/注释）；
  4. 备份任务排除 `flyway_schema_history` 的逻辑保留（与 Flyway 并存无冲突）；
  5. **Docker MySQL 8.0 联调验证（2026-08-04）**：全新库从 V1 全量迁移成功（`Successfully applied 1 migration to schema 'seitem'`）；应用启动时自动迁移成功（`Migrating schema to version "1 - init schema"` + `Started in 21.8s`）；二次启动幂等（`Schema up to date. No migration necessary`）；`/v1` 上下文与接口访问正常（HTTP 200）。

### H-07 接口完全无版本控制
- **优先级**：高
- **类别**：接口版本控制 / 架构
- **现状**：`/admin/**`、`/user/**`、`/knowledge/**`、`/museum/**` 均无 `/v1/` 前缀。
- **影响后果**：字段/语义变更即破坏旧客户端，无法平滑演进与双版本并行。
- **解决步骤**：
  1. 制定版本策略：URL 路径版本（`/v1/admin/**`）或 Header 版本二选一；
  2. 建议 URL 版本（对四端更直观），通过 `server.servlet.context-path` 或 controller `@RequestMapping` 统一加 `/v1`；
  3. 当前已发布的外部调用方确认无硬编码后一次性切换；
  4. 在 README/API 文档中固化版本约定。
- **状态**：已完成（代码侧） / 需联调验证
- **解决结果**：
  1. 采用 `server.servlet.context-path=/v1` 统一版本前缀，全部接口变为 `/v1/admin/**`、`/v1/user/**` 等；
  2. 拦截器路径无需改动（Spring 先剥离 context-path 再匹配拦截器）；
  3. 前端 `request.js`/`requestUser.js` baseURL 同步加 `/v1`，`vite.config.js` 代理匹配 `/v1` 前缀；

### H-08 前端高危依赖漏洞未修复（axios / postcss）

- **状态**：已完成

  2. `axios@1.19.0` 已超出受影响范围（<1.18.0），本地复跑 `npm audit --audit-level=high` 结果为 **0 漏洞**；
  3. `npm-audit-result.json` 已更新为通过后基线快照；
  4. CI 前端 job 已增加 `npm audit --audit-level=high` 门禁。

## 四、一般问题（Medium）

### M-01 前端 Token 存 localStorage 且无 XSS 防护
- **优先级**：高

### M-16 恢复功能：DDL 隐式提交导致"全量回滚"失效 + 逐条执行性能差（2026-08-05 新增整改）
- **优先级**：高
- **类别**：数据可靠性 / 性能
- **现状**（整改前）：`RestoreServiceImpl.executeSqlFile` 逐条 `st.execute(statement)` 执行；由于备份文件每张表含 `DROP TABLE + CREATE TABLE`（DDL），而 **MySQL 中 DDL 会隐式提交事务**，`conn.rollback()` 实际只能回滚最后一条 DDL 之后的 DML——"任一条失败即全量回滚"的声明是误导性的，失败后库会处于部分重建状态。
- **影响后果**：恢复中途失败时，用户误以为已完整回滚，实际库处于部分表已重建的中间状态；若未用应急备份兜底，将造成不可预期的数据状态。
- **解决步骤**：
  1. 重构 `executeSqlFile`：区分 DDL 与 DML；
  2. DML（INSERT 等）累积到 `Statement.addBatch`，每 200 条 `executeBatch` 批量执行（性能优化）；
  3. DDL（DROP/CREATE/ALTER/TRUNCATE/RENAME）单独 `execute`，且执行前先 flush 已累积的 DML batch；
  4. 语句截取时去除尾部多余分号（`trimStatement`），保证批量与判定准确；
  5. 失败时如实提示"因备份含 DDL（隐式提交），部分表可能已重建，请使用 before_restore 应急备份还原"，不再宣称已完整回滚；
  6. 移除无意义的 `TRANSACTION_READ_UNCOMMITTED` 设置。
- **状态**：已完成（已验证）
- **解决结果**：
  1. `executeSqlFile` 完成重构（DML 批量 + DDL 单独 + 如实回滚语义）；
  2. `flushBatchSafely` 统一处理 batch 失败（计数 + 记录详情 + 清空 batch）；
  3. 新增 `RestoreServiceImplTest` 4 用例（DML 走 batch、DDL 前 flush、失败回滚含应急备份提示、失败后跳过剩余）；
  4. 全量 40 个测试通过（BUILD SUCCESS），无回归。

## 五、轻微问题（Low）

### L-01 有数据恢复工具但无发布回滚 SOP
- **优先级**：中
- **类别**：回滚策略
- **现状**：备份/恢复功能存在，README 与 CI 无回滚流程。
- **影响后果**：发布失败时只能现场救火。
- **解决步骤**：
  1. 编写《发布与回滚操作手册》：制品版本化、回退上一版 jar/dist、数据库结构回退（Flyway 回滚策略）；
  2. 至少做一次发布/回滚演练并记录。
- **状态**：已完成（手册 + 脚本 + 演练）
- **解决结果**：
  1. 新建《docx/发布与回滚操作手册.md》：发布检查清单、标准发布流程、数据层/应用层回滚策略（Flyway 反向脚本规范、版本保留、符号链接切换）、回滚演练登记表；
  2. 新增 `deploy/` 脚本：`deploy.sh`（Linux 标准发布 + 版本归档 + current 符号链接 + 保留最近 N 版）、`rollback.sh`（Linux 回滚）、`rollback.ps1`（Windows 回滚）；
  3. 本地演练：应用发布状态验证通过（HTTP 200）→ 执行回滚脚本（停止→启动→健康检查链路可用）；
  4. **演练发现并修复**：回滚脚本未透传端口导致回滚后误用 8080 端口冲突，已修复为 `--server.port=$Port` 透传（`rollback.ps1`/`deploy.sh` 同步修复）；
  5. 已知限制：健康检查等待时长偏短（应用启动约 22s），脚本输出 WARN 提示人工确认（已在手册注明）。

### L-02 前端无 browserslist / 运行环境版本锁定
- **优先级**：低
- **类别**：兼容性
- **现状**：Vite 6 + Vue 3.4，无 browserslist、`.nvmrc`/`engines`。
- **影响后果**：构建目标与 Node 版本在团队内不一致。
- **解决步骤**：
  1. 增加 `.nvmrc`（Node 20）与 `package.json engines`；
  2. 增加 browserslist 声明或明确支持浏览器范围。
- **状态**：已完成
- **解决结果**：
  1. 新增 `relic-frontend/.nvmrc`（Node 20）；
  2. `package.json` 增加 `engines`（node >=18 <22, npm >=9）与 `browserslist`（现代浏览器 ≥ Chrome 80/Edge 80/FF 78/Safari 14）；
  3. JSON 校验通过。

### L-03 CI 前端未执行 lint 门禁
- **优先级**：低
- **类别**：代码质量
- **现状**：`ci.yml` 前端仅 build，未跑 `npm run lint`。
- **影响后果**：README 声称的 lint 清零无门禁保障。
- **解决步骤**：CI 前端 job 增加 `npm run lint` 步骤。
- **状态**：已完成
- **解决结果**：CI 前端 job 已增加 `npm run lint` 步骤，lint 未清零将阻断构建（与 H-08 audit 门禁并列）。

### L-04 前端构建产物（dist）未纳入版本跟踪
- **优先级**：低
- **类别**：环境配置一致性
- **现状**：`dist/` 被 gitignore，无产物校验机制。
- **影响后果**：发布制品来源不可审计。
- **解决步骤**：CI 产出制品（artifact）并记录 sha256，发布用 CI 制品而非本地构建。
- **状态**：已完成
- **解决结果**：
  1. CI 后端 job 增加 `mvn package` 与 `upload-artifact`（relic-server-jar），并输出 `sha256`；
  2. CI 前端 job 增加 `upload-artifact`（relic-frontend-dist），并输出 dist 目录整体校验和；
  3. 发布时以 CI 制品为准（见《发布与回滚操作手册》2.1 制品版本化）。
